# معماری پنل آیکو

## تصمیم اصلی: «مونولیت ماژولار»

یک برنامه، یک پروسه، یک استقرار، یک ورود — ولی داخلش ماژول‌های کاملاً جدا.

برای تیمی به اندازه آیکو (دو شریک، چند فروشنده، یک سرور ایرانی) این بهترین تعادل است:

| گزینه | چرا نه |
|---|---|
| چند برنامه جدا (وضعیت قبلی) | چهار ورود، چهار استقرار، چهار پشتیبان؛ داده‌ها به هم نمی‌رسند؛ ظاهرها جدا |
| میکروسرویس | هزینه عملیاتی (شبکه، صف، هماهنگی نسخه‌ها) برای تیم یک‌نفره سنگین است و سود مقیاس ندارد |
| **مونولیت ماژولار** | سادگی یک برنامه + مرزهای روشن بین بخش‌ها؛ هر ماژول اگر روزی لازم شد قابل جدا شدن است |

قواعدی که مرزها را نگه می‌دارد:

1. **هر ماژول داده خودش را دارد** — یک فایل SQLite جدا (`erp.db`، `pricing.db`، `media.db`). هیچ ماژولی جدول ماژول دیگر را JOIN یا ویرایش نمی‌کند.
2. **هویت مشترک است** — `core.db` (کاربران، نشست‌ها، دسترسی‌ها، رویدادها). هر اتصال ماژول آن را **فقط‌خواندنی** با نام `core` ضمیمه می‌کند تا بتواند نام کاربر را نشان دهد؛ نوشتن فقط از طریق `app.core`.
3. **ارتباط بین ماژول‌ها با رویداد** — مثلاً وقتی در «تیم» به کسی نقش «فروشنده» داده می‌شود، core رویداد `user.saved` را منتشر می‌کند و ERP حساب «پول نزد …» را برایش می‌سازد؛ core هیچ چیزی از ERP نمی‌داند.
4. **قرارداد ماژول** — هر ماژول در `app/modules/<id>/__init__.py` یک `Module(...)` اعلام می‌کند و core فقط همان را سوار می‌کند.

## نقشه

```
                   مرورگر / اپ نصب‌شده (PWA، RTL، claymorphism)
                    │  یک پوسته: ریل بخش‌ها + منوی بخش + صفحه‌ها
                    │  /static (کیت مشترک)   /m/<id>/index.js (صفحه‌های هر ماژول)
                    ▼
 Caddy (HTTPS) ──► uvicorn — یک پروسه، یک worker
                    │
        ┌───────────┴──────────────────────────────────────────────┐
        │ core                                                      │
        │  auth (scrypt، نشست با توکن هش‌شده، CSRF، نقش هر ماژول)  │
        │  events (رویدادهای زنده SSE + هوک‌های بین ماژول)         │
        │  activity (فید یکپارچه، زنگوله، ربات بله/تلگرام)          │
        │  jobs (زمان‌بندی مشترک + حلقه‌های پس‌زمینه با ری‌استارت)  │
        │  backup (شبانه روی سرور + هر ساعت در کانال تلگرام)         │
        │  integrations (ووکامرس، پروکسی خروجی، OpenRouter — مشترک)  │
        │  bot (ربات مدیران: گزارش، ثبت فروش/هزینه، پشتیبان)          │
        │  db (یک فایل برای هر ماژول، مهاجرت نسخه‌دار)              │
        └───┬──────────────────┬───────────────────┬────────────────┘
            │ /api/erp         │ /api/pricing      │ /api/media
        ┌───▼─────┐        ┌───▼──────┐        ┌───▼──────┐
        │ ERP     │        │ pricing  │        │ media    │   (chat بعداً)
        │ erp.db  │        │pricing.db│        │ media.db │
        │ ووکامرس │        │ خزنده‌ها │        │OpenRouter│
        └─────────┘        └──────────┘        └──────────┘
```

## قرارداد ماژول (بک‌اند)

```python
module = Module(
    id="pricing", name="قیمت رقبا", icon="chart-line",
    roles={"editor": "مدیر قیمت‌گذاری", "viewer": "فقط مشاهده"},   # بالاترین اول
    router=router,                       # → /api/pricing/...
    web_dir=Path(...)/"web",             # → /m/pricing/...
    databases=[db.database],             # مهاجرت، پشتیبان، سلامت
    startup=startup, shutdown=shutdown,  # کارگرها و زمان‌بندی‌ها
    notify={"crawl_done": "..."},        # کلیدهای اعلان ربات
    summary=summary,                     # کارت صفحه «خانه»
    event_filter=...,                    # چه رویدادهای زنده‌ای به چه کسی برسد
    cli={"crawl": ...},                  # python -m app pricing crawl
    bot={"prices": Report(label, fn),    # دکمه‌های ربات مدیران (core/botkit.py):
         "sale": SaleFlow()},            #   گزارش یک‌مرحله‌ای یا گفتگوی مرحله‌به‌مرحله
    exception_handlers={MyError: 400},
)
```

مسیرها دسترسی را اعلام می‌کنند و سرور اجرا می‌کند (نه فقط مخفی کردن در منو):

```python
Viewer = Depends(auth.require("pricing"))            # هر نقشی در این ماژول
Editor = Depends(auth.require("pricing", "editor"))  # editor یا بالاتر
```

## قرارداد ماژول (فرانت‌اند)

`/m/<id>/index.js`:

```js
export default {
  id, css: ["/m/<id>/<id>.css"],
  nav(role), mobile(role),            // منوی کناری و نوار پایین موبایل
  pages: { "": () => import("./pages/x.js"), ... },
  allowed(role, page),                 // صفحه‌های مجاز برای نقش
  enter(),                             // داده‌های اولیه ماژول، یک بار
  action(role), quick(role),           // دکمه نوار بالا، میانبر صفحه خانه
  glance(data, role),                  // صفحه خانه: { headline, stats: [...], alerts: [...] }
}
```

همه ماژول‌ها فقط از `/static/js/kit.js` (کیت مشترک: api، html، sheet، toast، ویجت‌ها، نمودار، تاریخ شمسی) و `/static/css/clay.css` (سیستم طراحی) استفاده می‌کنند؛ CSS هر ماژول فقط اجزای خاص خودش را اضافه می‌کند. رویدادهای زنده هر ماژول در کانال `live:<id>` می‌آیند.

## داده و تراکنش

* SQLite با WAL، `busy_timeout` و `synchronous=NORMAL`؛ نوشتن‌ها با `BEGIN IMMEDIATE`.
* هر فایل قفل نوشتن خودش را دارد: خزنده قیمت هیچ‌وقت پشت ثبت فروش صف نمی‌کشد.
* در WAL تراکنش روی چند فایل اتمیک نیست؛ برای همین اثرهای جانبی (ردیف فید رویداد، پیام ربات، رویداد زنده) **بعد از commit** تراکنش اصلی اجرا می‌شوند (`con.after_commit`). فروشی که برگشت بخورد هرگز در فید «فروخته شد» دیده نمی‌شود.
* مهاجرت‌ها: `app/<…>/migrations/NNNN_name.sql|py`، شماره در `PRAGMA user_version`. فقط رو به جلو؛ استقرار قبل از هر انتشار از همه پایگاه‌داده‌ها عکس می‌گیرد.

## چرا یک worker؟

زمان‌بند، رویدادهای زنده و قفل خزنده داخل پروسه‌اند. دو worker یعنی هر کار زمان‌بندی‌شده دو بار. ظرفیت یک worker برای این تیم چندین برابر نیاز است؛ اگر روزی لازم شد، فقط لایه انتقال `events` (مثلاً Redis) و زمان‌بند (قفل توزیع‌شده) عوض می‌شود و کد ماژول‌ها دست نمی‌خورد.

## امنیت

* رمزها scrypt؛ از نشست‌ها فقط SHA-256 توکن ذخیره می‌شود.
* کوکی HttpOnly + SameSite=Lax + هدر `X-Aiko` برای هر درخواست تغییردهنده (CSRF).
* محدودیت تلاش ورود (۸ بار در ۱۰ دقیقه برای هر IP).
* CSP سخت‌گیر (`script-src 'self'`، بدون اسکریپت درون‌خطی)، `X-Frame-Options: DENY`، `nosniff`.
* کلید OpenRouter و ووکامرس فقط روی سرور؛ پاسخ‌ها فقط «تنظیم شده/نشده» برمی‌گردانند.
* درخواست‌های تولید محتوا قبل از ارسال با فهرست مجاز فیلدها اعتبارسنجی می‌شوند (هیچ هزینه‌ای برای درخواست نامعتبر)؛ سقف هزینه ماهانه؛ خروجی SVG فقط به‌صورت دانلود.
* سرویس با کاربر بدون دسترسی `aiko` اجرا می‌شود.

## چیزهای مشترک بین همه بخش‌ها

* **اتصال‌ها** (`core/integrations.py`): آدرس و کلید ووکامرس (فروشگاه و قیمت رقبا هر دو از آن می‌خوانند)، پروکسی خروجی و کلید OpenRouter، یک بار در «تنظیمات» و در `core.db`. هر ارتباط با سرویس خارجیِ فیلترشده (تلگرام، OpenRouter) از `integrations.abroad_client()` یعنی از پروکسی می‌رود؛ سایت خودمان، بله و رقبا مستقیم.
* **صفحه خانه** عمداً خلوت است: کارهای سریع، چهار عدد اصلی، یک فهرست «نیاز به توجه» از همه بخش‌ها (و برای مدیر کل، تنظیمات ناقص که با یک لمس همان‌جا باز می‌شوند — `core/web/js/setup.js`) و آخرین رویدادها. هر ماژول با `glance()` سهمش را می‌دهد.
* **ربات مدیران** (`core/bot.py`): همان ربات اعلان‌ها با long polling. فقط چت‌های ثبت‌شده؛ ثبت فروش/هزینه فقط برای چتی که به یک مدیر کل فعال وصل است و این در هر مرحله دوباره چک می‌شود. ماژول‌ها دکمه‌هایشان را با `Module.bot` می‌دهند و هیچ‌کدام از تلگرام چیزی نمی‌دانند.
* **متن و عدد فارسی** (`core/text.py`): ارقام فارسی، مبلغ تومان و یکسان‌سازی نوشتار (ي/ی، ك/ک، نیم‌فاصله، ارقام) برای جستجو.

## اتصال سایت (`modules/erp/site/`)

| فایل | کار |
|---|---|
| `client.py` | تنظیمات، کلاینت HTTP ووکامرس، خواندن کاتالوگ، گزارش همگام‌سازی، وب‌هوک‌ها |
| `orders.py` | سفارش سایت ← فروش با مبلغ دقیق؛ با وب‌هوک فوری و هر چند دقیقه برای اطمینان؛ هر سفارش یک فروش (با شناسه سفارش) |
| `matching.py` | کدام محصول پنل کدام محصول سایت است (اول کد/SKU)، ساخت محصول برای محصول تازه سایت، پیشنهاد ادغام تکراری‌ها |
| `stock.py` | موجودی + کارگر پس‌زمینه |
| `history.py` | وارد کردن همه سفارش‌های قدیمی (یک بار، دستی)؛ هر شب بررسی دوباره سفارش‌های دو هفته اخیر |

قاعده‌ها، مثل اتصال‌های رسمی ووکامرس با صندوق‌ها:

* **موجودی یک جا نگه داشته می‌شود — پنل — و سایت همیشه همان عدد را نشان می‌دهد.** هر تغییر موجودی در پنل چند ثانیه بعد دقیقاً همان عدد را در سایت می‌گذارد؛ سفارش‌های سایت به‌صورت فروش وارد پنل می‌شوند؛ موجودی‌ای که دستی در وردپرس عوض شود به عدد پنل برمی‌گردد و گزارش می‌شود. تا بعد از روشن شدن برنامه یک بار همه محصولات با سایت مقایسه نشده باشد (و شمارش دستی اعمال نشده باشد)، چیزی به سایت فرستاده نمی‌شود. محصولی که سایت تعدادش را نمی‌شمارد با اولین اصلاح موجودی در پنل عدد می‌گیرد.
* **مشخصات محصول مال سایت است**: محصول/رنگ تازه، نام، عکس، قیمت و کد (SKU) از سایت به پنل می‌آید.
* **هر کالای قابل فروش (هر رنگ) یک کد یکتا دارد، یکسان در هر دو طرف.** اگر محصولی در سایت کد ندارد، با یک دکمه کد پنل روی آن نوشته می‌شود و از آن به بعد محصولات تازه هم خودکار کد می‌گیرند.
* **شمارش دستی کامل** (`modules/erp/data/stock_count_*.json`: شناسه محصول/رنگ سایت ← تعداد شمرده‌شده و قیمت خرید هر عدد، به‌علاوه کالاهای فقط انبار) یک بار، در اولین بررسی کامل بعد از استقرار، روی همان فروشگاهی که برایش ساخته شده اعمال می‌شود (بیشتر شناسه‌هایش باید در کاتالوگ باشد) و پنل آن را به سایت می‌فرستد. محصولی که به کل یک محصول رنگ‌دار وصل است اول به رنگ‌ها تفکیک می‌شود. شمارشی با `"tidy": true` قبلش انبار را فقط به کالاهای سایت می‌رساند: محصولی که به سایت وصل نیست اگر به‌وضوح همان یک محصول بی‌رنگ سایت است با آن ادغام می‌شود (فروش‌ها و خریدهایش هم منتقل می‌شود)، وگرنه با موجودی صفر بایگانی می‌شود و فروش‌هایش در گزارش‌ها می‌ماند. ربات تلگرام هم از همین انبار پنل می‌خواند.
* **ایمنی**: وب‌هوک برای سرعت، بررسی دوره‌ای (هر چند دقیقه محصولات تغییرکرده، هر نیم ساعت همه، هر شب سفارش‌های دو هفته اخیر) برای وقتی که وب‌هوکی گم شود؛ هر کار در گزارش ثبت می‌شود.

## صورت‌های مالی (`modules/erp/statements.py`)

سه صورت استاندارد، از همان دفتری که بقیه صفحه‌ها می‌خوانند (هیچ حسابداری جداگانه‌ای که باید هماهنگ بماند):

* **ترازنامه** در پایان دوره: نقد حساب‌های فروشگاه، پول نزد فروشنده‌ها، طلب از مشتری‌ها، موجودی کالا به میانگین قیمت تمام‌شده؛ در برابر بدهی به فروشنده‌ها و حقوق شرکا (آورده خالص هر شریک — همان «سهم» صفحه شرکا — و سود انباشته). پنل دوطرفه (double-entry) نیست، پس ترازنامه با یک خط توضیح‌داده‌شده بسته می‌شود: کالایی که بدون پرداخت ثبت‌شده وارد انبار شده منهای کسری انبار.
* **سود و زیان** دوره: فروش، تخفیف، برگشت، ارسال → درآمد خالص → بهای تمام‌شده → سود ناخالص → هزینه‌های جاری به تفکیک دسته → سود خالص.
* **جریان نقدی** دوره: حساب‌های فروشگاه و پول نزد فروشنده‌ها از نقد ابتدا تا نقد پایان؛ کارت شخصی شرکا نقد فروشگاه نیست.

هر صورت فهرستی از ردیف‌هاست ({label, amount, kind, indent, hint})؛ صفحه و فایل اکسل هر دو همان را نشان می‌دهند.

## رسیدها در گوگل درایو (`core/drive.py`, `modules/erp/receipts.py`)

رسید هر خرید، فروش و هزینه و فاکتور PDF هر سفارش سایت در درایو خود مدیر، در یک پوشه مرتب: `پنل آیکو — رسیدها/۱۴۰۵/۰۷ مهر/خرید کالا/۳۰ — P-12 — بازار تهران — ۸۳۰٬۰۰۰ تومان.jpg`.

* اتصال یک بار با حساب گوگل خود مدیر (OAuth). سرویس اکانت در درایو شخصی فضا ندارد، پس راه درست همین است. دسترسی فقط `drive.file`: پنل فقط فایل‌هایی را که خودش ساخته می‌بیند. برنامه گوگل باید «In production» باشد وگرنه اجازه بعد از ۷ روز باطل می‌شود. همه درخواست‌ها از پروکسی خروجی.
* صف در `core.db` (`drive_files`)؛ کارگر پس‌زمینه می‌فرستد، خطا را دوباره امتحان می‌کند، و وقتی رسید یک رکورد عوض شود نسخه قبلی را به سطل زباله درایو می‌برد. فایل‌ها روی سرور هم می‌مانند.
* کنترل حجم: عکس‌ها موقع بارگذاری به ۱۶۰۰ پیکسل و JPEG کیفیت ۸۰ کوچک می‌شوند (معمولاً ۱۵۰ تا ۴۰۰ کیلوبایت)، PDF حداکثر ۵ مگابایت، فاکتور سایت حدود ۲۰ کیلوبایت، و سقف کل (پیش‌فرض ۲ گیگ) — بعد از آن فایل‌ها روی سرور می‌مانند و یک بار خبر داده می‌شود.
* ماژول‌ها فقط `drive.enqueue(ref, path, folder, name)` را صدا می‌زنند و به رویداد `drive.backfill` (ارسال رسیدهای قبلی) جواب می‌دهند.

## افزودن ماژول جدید (مثلاً چت‌بات)

1. `app/modules/chat/` با `__init__.py` (اعلام `Module`)، `router.py`، `migrations/0001_init.sql`، `web/index.js`.
2. `MODULES=erp,pricing,media,chat` در `.env`.
3. اگر به داده ماژول دیگری نیاز دارد، از `api.py` آن ماژول یا رویدادها استفاده کند — نه از جدول‌هایش.

چت‌بات فعلی (`../Chatwoot`) طوری نوشته شده که این انتقال ساده است: موتور قطعی + کانال‌ها + کلاینت ووکامرس فقط‌خواندنی. هویت مشتری (Customer 360) پایگاه‌داده خودش می‌شود (`chat.db`).
